# Reward Design Expert Knowledge

## Five Questions — Answer Before Writing ANY Code

Answer these in your code's docstring and comments:

**Q1: What is the exact definition of task success?**
  → Extract from "Termination Outcomes Classification". Translate directly to Python:
    `self.xxx == True` or `not self.xxx.awake` etc. This becomes your terminal objective condition.

**Q2: What phases must the agent go through from start to success?**
  → From "Expected Trajectory Phases". One phase = at least one progress signal.

**Q3: What spatial constraints must the agent satisfy?**
  → CRITICAL: Does the task have a target region (landing pad, track lane, goal area)?
    Does leaving a region cause failure (out-of-bounds, wall collision)?
    → If YES: you MUST include a progress signal that rewards APPROACHING and STAYING
      within the target region. Pure stability + descent signals will NOT prevent drift.
    → For landing tasks: reward proximity to the landing zone center. For racing tasks:
      reward staying on track. For navigation: reward reducing distance to goal.

**Q4: For each phase, what SHOULD happen and what SHOULD NOT?**
  → SHOULD = what your progress signals encourage. SHOULD NOT = what regularizers suppress.

**Q5: Can random exploration discover success?**
  → Yes → a sparse terminal signal may suffice.
  → No → you need a chain of progress signals. Most continuous-control tasks need this.

## Reward Architecture — Three Layers (diagnostics don't count)

### Layer 1: Terminal Objective Signal
- `scale if success_condition else 0`
- Scale: the single largest positive reward. Use it as the anchor.
- Rule of thumb: terminal objective must exceed the maximum farmable total of any incorrect behavior.
  If hovering for 1000 steps can earn 400 from progress signals, terminal must be 500+.

### Layer 2: Progress Signals (1–4 components)
- At least one per trajectory phase, INCLUDING spatial constraint phases.
- **Delta form is the default**: `scale * max(0, prev - curr)` — only rewards improvement.
  Once target is reached, delta saturates to zero → immune to farming.
- **Exponential proximity** for approaching a target value: `scale * exp(-|curr - target| / sigma)`.
- **One-shot / event-gated** for milestones: `scale if condition AND not already_triggered`.
- If you use a non-delta form, explain in comments WHY delta was not applicable.

### Layer 3: Regularization Signals (0–2 components)
- ONLY for specific identified bad behaviors from the environment document.
- No bad behavior identified → no regularizer needed. Start with zero.
- Scale must be small enough to not dominate the episode return.
- PREFER redirecting with positive signals over suppressing with penalties.

### Diagnostics (not a layer — contribute zero to total reward)
- Expose key quantities in individual_reward at scale 0.0 for downstream analysis.

## Scale Rules

1. **Anchor first**: set terminal objective scale.
2. **Progress signals**: 0.1×–0.5× of terminal objective per episode.
3. **Regularization**: ≤ 0.1× of terminal objective per episode.
4. **Dominance check**: NO single auxiliary (non-terminal) component should exceed 2× the terminal
   objective in expected per-episode return. If it does, your reward will train the wrong behavior.

## Complexity Rule

Target: 1 terminal + 2–4 progress + 0–1 regularizer. Maximum 6 non-diagnostic components.

**Merge related metrics**. |angle| + |angular_vel| + |horiz_vel| = one "instability" signal.
Eight state dimensions are NOT eight design problems.

**But don't under-design either**. If the task requires approach, descent, AND touchdown precision,
three progress signals are appropriate. One signal cannot guide three distinct phases.

## Reward Hacking Defenses

- **Farming**: any positive per-step signal → convert to delta or one-shot.
- **Passivity**: if all components are penalties → agent learns to do nothing. Ensure a positive
  path exists.
- **Drift**: if no spatial centering signal → agent will drift off-target. Q3 is mandatory.
- **Timeout local optimum**: if progress signals pay per-step and terminal is one-shot, the agent
  may prefer to accumulate progress forever over risking the terminal action.
  → Ensure terminal > max_farmable. Add mild time pressure if needed.

## Interaction Audit (MANDATORY — do BEFORE finalizing code)

For EVERY dangerous behavior listed in the environment document PLUS "drifting off-target /
out-of-bounds" (even if not explicitly listed), AND for the intended success path, estimate:

| Behavior | Per-step signals | × Steps | + Terminal | = Total |
|----------|-----------------|---------|------------|---------|
| ... | ... | ... | ... | ... |
| **Successful landing** | ... | ... | +terminal | **total** |

**If any incorrect behavior earns ≥ 80% of the success path total, you have a local optimum. FIX IT.**

Check specifically:
- Hovering without landing: do progress signals accumulate to beat terminal?
- Drifting off-target: does the spatial signal adequately penalize drift?
- Doing nothing: does passivity earn more than attempting the task?
