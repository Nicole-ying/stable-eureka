# Reward Design Expert Knowledge

The following is framework-built-in, transferable reward-design methodology.
Apply it as you write your code.

## Questions to Answer Before Designing

Before writing any code, answer these four questions mentally, then reflect the
answers in your code's docstring and comments:

Q1: What is the exact definition of task success?
  → Extract the precise success condition from the environment document's
    "Termination Outcomes Classification" section. Your terminal objective
    condition must be a direct Python translation of this condition.

Q2: What phases does the agent need to go through from start to success?
  → Extract from "Expected Trajectory Phases". Each phase = one progress signal.

Q3: For each phase, what SHOULD happen and what SHOULD NOT?
  → SHOULD = what your progress signals encourage. SHOULD NOT = what regularizers suppress.

Q4: Can random exploration discover success?
  → Yes → a sparse terminal signal may suffice.
  → No → design a chain of progress signals. Most environments need this.

## The Four-Layer Reward Architecture

Design in priority order:

### Layer 1: Terminal Objective Signal
- Form: `scale if success_condition else 0`
- The condition MUST be a direct Python translation of the exact success condition
  from the environment document's "Termination Outcomes Classification".
- `self` IS the environment instance. Any `self.xxx` described in the environment
  document is directly accessible in your code.
- Scale: the single largest positive reward. Use it as the anchor.

### Layer 2: Progress Signals
- At least one per trajectory phase. Tell the agent it is on the right path.
- Choose the mathematical form based on what you want to encourage:

  Reduce a quantity     → `scale * max(0, prev - curr)`         (delta)
  Approach a target     → `scale * exp(-|curr - target| / sigma)` (exponential proximity)
  Mark a sub-goal       → `scale if condition AND one-shot`      (use self._flag)
  Maintain a state      → `scale if condition else 0`            (condition trigger)

- **Prefer delta forms.** Delta requires the agent to IMPROVE to earn reward.
  Once the agent reaches the target state, improvement saturates and the reward
  stops — making it immune to farming by stagnation.
- If you choose exponential proximity or condition-trigger forms, you MUST
  explain in the code comment why delta is not applicable for this signal.

### Layer 3: Regularization Signals
- Only for specific, identified bad behaviors. No bad behavior → no regularizer.
- Forms: `-scale * |x|`, `-scale * x^2`, or `-scale * max(0, x - margin)`.
- Scale must be small enough to not dominate the episode return.

### Layer 4: Diagnostic Signals
- Exposed in individual_reward but contribute zero to total reward.
- Pure observation. Do not affect agent learning.

## Scale Reasoning

Estimate per-episode expected contribution:
    E[total_per_episode] ≈ scale × firing_probability_per_step × expected_steps

Order: terminal objective first (anchor) → progress signals (0.1x–0.5x of objective)
→ regularization (far smaller than progress).

## Complexity Principle

Start simple: 1 terminal objective + 1–3 progress signals + 0–1 regularizers.
No more than 6 non-diagnostic components total.

You do NOT need a separate progress signal for every trajectory phase.
One well-chosen signal (e.g., reducing combined velocity+angle instability)
can guide the agent through multiple phases at once.
Choose the fewest signals that can lead to success — every extra component
multiplies interactions in ways you cannot predict.

## Reward Hacking Defenses (design-time)

- **Farming defense**: If a positive signal COULD fire every step for the wrong reason,
  make it one-shot or event-gated.
- **Do-nothing defense**: Ensure "doing nothing" earns nothing. If every action
  produces only penalties, the agent learns to be passive.
- **Sparse blindness defense**: If success is too far, build a chain of progress
  signals that lead toward it step by step.
- **Over-gating defense**: A single reward term should have ≤ 2 gating conditions.

## Multi-Component Interaction Audit (REQUIRED before finalizing)

Using YOUR reward code, estimate the per-episode total return for EACH dangerous
behavior listed in the environment document, AND for the intended success path.

If any dangerous behavior earns MORE than the success path, your reward function
has a local optimum. The agent will learn the dangerous behavior instead of the task.

Fix: convert the farmable signal to delta form, or ensure the terminal objective
exceeds the farmable total over a full episode.
