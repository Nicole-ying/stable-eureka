# Reward Revision Expert Knowledge

The following is framework-built-in methodology for iterative reward debugging.

## Your Role

You are a debugger, not a redesigner. The current reward has been trained and produced data.
Your job is to find the root cause and apply a single, targeted fix.

## Diagnostic Order

Read the diagnostics and answer these questions in order:

1. Look at the Component Returns table. Which component dominates the total return?
   Which component is always zero? Does the terminal objective ever fire?

2. Look at the Terminal Outcome Distribution. Which outcome does the agent reach most often?
   Why is it reaching that outcome instead of success?

3. Look at the Behavior Summary and Trajectory Examples. What is the agent actually doing?
   Compare against the dangerous behaviors listed in task_model.md.

4. Trace the reward: WHY is the agent choosing this behavior given the current reward structure?
   Which components reward the bad behavior or penalize the good behavior?

## Common Failure Patterns

These patterns emerge across environments. When you recognize one:

- **Reward farming**: A positive component fires repeatedly, dominates total return,
  but success=0. It lacks protection (one-shot, event-gating, or delta form).
- **Semantic error**: The terminal objective condition does not match the environment's
  true success flag as defined in task_model.md.
- **Weak shaping**: All progress signals together contribute < 5% of total return.
  The agent receives almost no guidance.
- **Penalty dominance**: Nearly all non-diagnostic components are negative.
  The agent learns passivity — doing nothing is the optimal strategy.

## Editing Principles

- Prefer editing 1 component. If you must edit multiple, explain why they must be co-edited
- If the root cause is unclear: edit the dominant component (largest contributor)
- Record your hypothesis: what you changed, why, what you expect to change, what evidence
  will confirm or refute it
- Direction guide:
  - Condition too strict → relax it
  - Scale too strong → reduce it
  - Farmable form (unconditional per-step positive) → convert to delta or one-shot
  - Always-zero component → relax condition or remove it

### Removing components (cleanup — does NOT count as an edit)

You may REMOVE components that meet ALL of these criteria:
1. They contribute < 1% of total episode return (effectively dead)
2. They serve no diagnostic purpose (their value is obvious from other components)
3. Removing them simplifies the reward structure without losing useful signal

This is cleanup, not editing. You can remove multiple dead components in one revision.
But you MUST explain why each removed component was unnecessary.

Excess components create untestable interactions. 3 components have 3 pairwise
interactions; 8 components have 28. If the reward feels cluttered, clean up.

## Anti-Patterns

- Do NOT add a new component to fix a problem caused by an existing one. Fix the existing one.
- Do NOT tune multiple scales at once. One at a time.
- Do NOT add penalties to suppress behavior that a positive signal could redirect.
- Do NOT repeat edit patterns listed as forbidden in expert_memory_context.md.
- If the agent already succeeds in some episodes, make small adjustments only.
